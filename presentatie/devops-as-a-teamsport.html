Chapter 2

Conway’s Law & Team Topologies

Chapter 2 · Architecture & Org

Conway’s Law

“Organizations which design systems are constrained to produce designs which are copies of the communication structures of these organizations.”
— Melvin Conway, 1967

Chapter 2 · Architecture & Org

Conway’s Law - Examples

Tech oriented teams (f.e. Java, React, Ops)

Every team has their own expertise. They lack the skill, knowledge, concerns and pitfalls of the other tech stacks.

Target group oriented teams (Customers, Service Desk, Admins)

Every team or domain usually has strong overlap or dependency to the other teams.

Your codebase(s) and related systems are a mirror of how your people talk (or don't talk).

Chapter 2 · The Silo Trap

The "Hero Developer/Ops" Anti-Pattern

Siloed Ownership

  • "Don't touch that module, only Sarah knows how it works."
  • Tickets are assigned to individuals, not the team.
  • 🔥 Legendary expression 🔥:
    This is my application.

Bus Factor = 1

  • Sarah goes on holiday → production bug → panic.
  • Knowledge stays trapped in heads instead of shared across the team.
Chapter 2 · Team Topologies

Designing Teams for Fast Flow

1. Stream-Aligned

End-to-end delivery of value for a specific product or domain.

2. Platform

Provides internal self-service tools & infra to reduce cognitive load.

3. Enabling

Helps stream-aligned teams adopt new skills and practices.

4. Complicated-Subsystem

Handles heavy specialist math, AI models, or legacy cores.

How Do Engineers Share Knowledge?

Chapter 3 · The Spectrum

From Silos to Collective Ownership

0. Not at all 🙃
→
1. Async PRs
→
2. Pair Review
→
3. Pair Prog.
→
4. Mob Prog. & XP

Moving right = higher communication bandwidth & faster feedback loops.

Level 0 · Not at all 🙃

Individual

  • "Works on My Machine"
  • Direct push to main, zero reviews, zero tests.
  • "I'll document it later" (spoiler: later never comes).
  • I'm a hero (developer/ops) ♬
  • Result: Feels blazingly fast on Day 1, turns into untouchable legacy code by Month 2.
Level 1 · Pull Requests & Code Review

The Async Pull Request Trap

  • Very common
  • Built for open-source strangers — often abused inside teams.
  • Waiting time & context switching: Code sits idle for hours or days.
  • Too late for architecture feedback: Nobody wants to rewrite 600 lines after the work is "done".
  • The classic 800-line PR → "LGTM 👍" (nobody actually read it).
Level 2 · Pair Review

Upgrade: Synchronous Pair Review

  • Walk through the PR together (at one desk or on a quick call).
  • Why it’s better: Instant context, zero passive-aggressive text comments, real knowledge transfer.
  • Limitation: Still happens after the code has already been written in isolation.
Level 3 · Pair Programming

Two Brains, One Keyboard

  • Continuous code review while writing, not days later.
  • One thinks tactically (the code), the other thinks strategically (edge cases, design, next steps).
  • Prevents rabbit holes and spreads domain knowledge automatically.
Level 4 · Ensemble Programming & XP

A Whole Team Approach

“All the brilliant minds working together on the same thing, at the same time, in the same space, and at the same computer.”
— Woody Zuill

  • XP Principle: If code reviews are good → review continuously. If communication is key → talk constantly.
  • Zero handoffs, zero waiting, zero silos. Everyone understands the system.
Chapter 3 Bonus · XP

XP Advantages

  • TDD (Make it red, make it green, make it clean)
  • Continuous Integration (real CI/CD)
  • Continuous Refactoring (always have the confidence to improve existing codebase)
Chapter 3 Bonus · AI in the Mix

Where Does AI Fit In? 🤖

  • AI is a tool, not a teammate: Domain knowledge and ownership still belong in human heads.
  • AI = The Ultimate Driver: Great at typing fast, generating boilerplate, and suggesting syntax.
  • Humans = The Navigators: You set the direction, ask the right questions, and verify the result.
  • If you can’t navigate a human Driver, you won’t be able to navigate AI either.
Chapter 3 · Nuance

Pick one, forget the others?

  • Teams need to be sized accordingly.
  • Usually a combination works best
  • Organization (a.k.a. architectural/domain) structure matters

Chapter 4

Workshop: Mob Programming in Action

Workshop · Rule #1

Psychological Safety First

  • Mobbing only works if it is 100% safe to say: "I don't know" or "Can you explain that?"
  • Treat every teammate with kindness, patience, and respect.
  • During a mob, there is no hierarchy
  • No Trust = No Team
Workshop · Roles & Rotation

How a Mob Works

⌨️ Driver (1 person)

Controls the keyboard. Listens and translates the Navigator’s intent into code. Does not decide the direction.

🧭 Navigator (1 person)

Decides what we do next and why. Speaks at the level of intent, not keystrokes.

👀 Spectators (Rest of the Mob)

Think along, look up docs, spot edge cases

⏱️ 5-Minute Timer

Rotate roles every 5 minutes!

Workshop · Hands-On

Your Turn: FizzBuzz Kata (TDD)

  • Form mobs of 4–5 people around 1 laptop.
  • Write a failing test first, then make it pass.
  • Rotate Driver and Navigator every 5 minutes!
  • Rules: %3 → "Fizz", %5 → "Buzz", %15 → "FizzBuzz", else str(n).
Your Turn: FizzBuzz Kata (Shell/Bash)

Scenarios

  • input null → Output null
  • input 1 → Output 1
  • input FizBuz → Output FizBuz
  • input 3 → Output Fizz
  • input 5 → Output Buzz
  • input 15 → Output FizzBuzz
Your Turn: FizzBuzz Kata (Shell/Bash)

    source "${BATS_TEST_DIRNAME}/fizzbuzz.sh"
}

    [ "$status" -eq 1 ]
    [ "$output" = "Error: Valid positive integer required" ]
}
